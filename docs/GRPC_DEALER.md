# Converting dealer_repl to gRPC Service

This guide explains how to transform the interactive `dealer_repl` REPL into a 
message-driven gRPC service.

## Overview

The current `dealer_repl` is a command-line REPL that directly manages a `Dealer` 
instance. A gRPC version would:

1. Run the `Dealer` as a network service that clients can connect to
2. Support multiple concurrent clients (each managing their own table)
3. Enable remote clients in any language (Go, Python, Java, etc.)
4. Provide streaming updates for real-time game state changes

## Architecture

```
┌──────────────┐         gRPC          ┌──────────────┐
│              │  ───────────────────>  │              │
│   Client     │                        │    Server    │
│   (any lang) │  <───────────────────  │   (Rust)     │
│              │     Responses          │              │
└──────────────┘                        └──────────────┘
                                               │
                                               │ manages
                                               ▼
                                        ┌──────────────┐
                                        │   Dealer     │
                                        │   + Table    │
                                        └──────────────┘
```

## Setup

### 1. Add Dependencies to Cargo.toml

```toml
[dependencies]
# Existing dependencies...
tonic = "0.12"
prost = "0.13"
tokio = { version = "1.42", features = ["macros", "rt-multi-thread"] }

[build-dependencies]
tonic-build = "0.12"
```

### 2. Create build.rs

Create a `build.rs` file in the project root to compile the proto files:

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    tonic_build::configure()
        .build_server(true)
        .build_client(true)
        .compile_protos(&["proto/dealer.proto"], &["proto"])?;
    Ok(())
}
```

### 3. Protocol Buffer Definition

See `proto/dealer.proto` for the complete service definition.

## Implementation

### Server Implementation (examples/dealer_grpc_server.rs)

The server needs to:
- Implement the `DealerService` trait generated by tonic
- Manage concurrent dealer instances (one per client session)
- Handle all the RPC methods

Key considerations:
- **Thread safety**: Use `Arc<Mutex<Dealer>>` or `Arc<RwLock<Dealer>>` for 
  concurrent access
- **Session management**: Track multiple tables/dealers if supporting multiple 
  concurrent games
- **Error handling**: Convert `DealerError` to gRPC status codes

### Client Implementation (examples/dealer_grpc_client.rs)

The client:
- Connects to the server
- Calls RPC methods instead of direct `Dealer` methods
- Can be implemented in any language with gRPC support

## Advantages of gRPC over REPL

1. **Remote Access**: Clients can connect from anywhere
2. **Language Agnostic**: Write clients in Python, Go, JavaScript, etc.
3. **Structured APIs**: Type-safe, auto-generated code
4. **Scalability**: Multiple clients, load balancing, horizontal scaling
5. **Streaming**: Server can push real-time updates to clients
6. **Testing**: Easy to write integration tests with gRPC clients

## Multi-Client Support

For supporting multiple concurrent games:

```rust
// In the server
struct DealerServiceImpl {
    dealers: Arc<Mutex<HashMap<String, Arc<Mutex<Dealer>>>>>,
}

// Each RPC call includes a session_id to identify which dealer to use
```

## Streaming Events

The `StreamEvents` RPC enables real-time push notifications:

```rust
// Server sends events whenever something happens
stream.send(TableEvent {
    timestamp: now(),
    event_type: EventType::PlayerAction,
    description: "Seat 2 bets 400".to_string(),
    current_status: Some(build_status(&dealer)),
}).await?;
```

Clients can subscribe to this stream and update their UI in real-time.

## Example Usage

### Starting the server:
```bash
cargo run --example dealer_grpc_server
```

### Using a Rust client:
```bash
cargo run --example dealer_grpc_client
```

### Using a Python client:
```bash
python3 dealer_client.py
```

## Migration Path

1. **Phase 1**: Implement basic gRPC server with all core operations
2. **Phase 2**: Add streaming events for real-time updates
3. **Phase 3**: Add authentication and session management
4. **Phase 4**: Deploy with proper error handling and monitoring
5. **Phase 5**: Build web UI or mobile app clients

## Security Considerations

For production use:
- Add TLS encryption
- Implement authentication (JWT tokens, mTLS, etc.)
- Rate limiting to prevent abuse
- Input validation (already done by Dealer)

## Testing
