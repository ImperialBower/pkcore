## 1. Circular array scan (modular index) — `next_occupied_seat_after`

- **Where:** `src/casino/table.rs:781-799`; also `src/casino/table/seats.rs:397-430` (`next_to_act`)
- **Level:** Warm-up
- **Pattern:** circular array traversal with `(start + step) % size`
- **Code now:**
  ```rust
  pub fn next_occupied_seat_after(&self, start: u8, n: usize) -> u8 {
      let size = self.seats.0.len();
      if size == 0 {
          return 0;
      }
      let occupied: Vec<u8> = (1..=size)
          .filter_map(|step| {
              let idx = (start as usize + step) % size;
              // ... skip empty seats
          })
          .collect();
      // ... fallback when no seat is occupied
      let idx = (n - 1) % occupied.len();
      occupied[idx]
  }
  ```
- **What it does now:** It walks once around the table, starting after
  `start`, and keeps the occupied seats. Then it picks the n-th one, wrapping
  again with `%`. Cost of the excerpted site: O(seats) time and O(seats)
  space for the `Vec` (read). With `n = 0`, line 797 panics with "attempt to
  subtract with overflow" (ran). All current callers pass `n = 1`.
- **Learn:** A circular buffer is a flat array where index `size` wraps back
  to `0`. Every "next seat clockwise" question is `(i + 1) % size`. Edge
  cases sit at `0` and at `size`: look up "off-by-one error" and "ring
  buffer" in any data structures text.
- **Exercise:** Write
  `fn nth_occupied_after(occupied: &[bool], start: usize, n: usize) -> Option<usize>`.
  It returns the n-th occupied index clockwise after `start` (n starts at 1),
  wrapping as often as needed, with no heap allocation. First test:
  `nth_occupied_after(&[true, false, true], 0, 1) == Some(2)`.
- **Done when:** `n = 0` and an all-empty table return `None` and do not
  panic; `nth_occupied_after(&[true, false, true], 0, 3) == Some(2)`
  (wraps past seat 0 and back).
- **Exercism:**
  [Circular Buffer](https://exercism.org/tracks/rust/exercises/circular-buffer)
  (difficulty 10) — the read and write heads advance with the same
  `% capacity` wrap as the seat scan.
  `exercism download --track=rust --exercise=circular-buffer`
- <details><summary>Hint</summary>Count down `n` while you step
  `idx = (idx + 1) % size`, and stop after `size * n` steps at most. Make
  `n = 0` an explicit early return. Target: O(seats) time, O(1) space.</details>

## 2. Duplicate detection: pairwise vs set / bitset — `Pile::are_unique`

- **Where:** `src/lib.rs:921-924`; `src/arrays/mod.rs:50-52` (macro copy for
  the fixed arrays); `src/arrays/sliced.rs:449-451` (set-based version)
- **Level:** Warm-up
- **Pattern:** element distinctness (all-pairs scan vs hash set vs bitset)
- **Code now:**
  ```rust
  /// This code is cribbed from [`oli_obk`](https://stackoverflow.com/a/46766782/1245251).
  fn are_unique(&self) -> bool {
      let v = self.to_vec();
      !(1..v.len()).any(|i| v[i..].contains(&v[i - 1]))
  }
  ```
- **What it does now:** For each card, it scans every card after it. Cost of
  the excerpted site: O(n²) compares plus one `Vec` allocation (read). For a
  `Seven`, n = 7, so this is 21 compares. The `sliced.rs` version builds a
  set and compares lengths: O(n) time, O(n) space (read).
- **Learn:** Element distinctness has three classic answers: all pairs
  O(n²), sort then check neighbours O(n log n), or a hash set O(n). When the
  universe is small and fixed (52 cards), a bitset is a hash set with no
  hashing: one `u64`, one bit per card. Look up "element distinctness
  problem".
- **Exercise:** Write `fn all_distinct(cards: &[u8]) -> bool`, where each
  card is an index `0..52`. Use one `u64` as the seen-set. First test:
  `all_distinct(&[0, 13, 51]) == true` and `all_distinct(&[5, 5]) == false`.
- **Done when:** It agrees with the O(n²) version on 10,000 random slices of
  length 0–52, and it does no heap allocation.
- **Exercism:**
  [Isogram](https://exercism.org/tracks/rust/exercises/isogram)
  (difficulty 4) — "no repeated letter" is the same distinctness test over a
  26-letter universe, and a `u32` bitmask solves it.
  `exercism download --track=rust --exercise=isogram`
- <details><summary>Hint</summary>For each card: `let bit = 1u64 << card;`
  if `seen & bit != 0`, return false; else `seen |= bit`. Target: O(n) time,
  O(1) space.</details>

## 3. Bit tricks: popcount + contiguous run of set bits — `Five::is_straight`

- **Where:** `src/arrays/five.rs:106-112`
- **Level:** Warm-up
- **Pattern:** bitset of ranks; popcount; "are the set bits contiguous?"
- **Code now:**
  ```rust
  pub fn is_straight(&self) -> bool {
      let rank_bits = self.or_rank_bits();
      // DEFECT_034: the span test alone passed `9 9 9 9 5`; a pair shares a bit.
      rank_bits.count_ones() == 5
          && (((rank_bits.trailing_zeros() + rank_bits.leading_zeros()) == Five::STRAIGHT_PADDING)
              || rank_bits == Five::WHEEL_OR_BITS)
  }
  ```
- **What it does now:** It ORs the five rank bits into one 13-bit mask. Five
  set bits means five different ranks. If the zeros on both sides add up to
  27 (32 − 5), the five bits sit side by side. The wheel `A-2-3-4-5` is a
  special case. Cost of the excerpted site: O(1), three bit instructions
  (read). Checked: `AKQJT` and `5432A` are straights; `9999 5` and `K A 2 3 4`
  are not (ran).
- **Learn:** A set of small integers fits in one machine word. Popcount
  gives its size; trailing and leading zeros give its lowest and highest
  member. A run of k set bits is also "mask divided by its lowest bit equals
  2^k − 1". Look up "Hacker's Delight, chapter 2" or "bit twiddling hacks".
- **Exercise:** Write `fn is_run_of(mask: u16, k: u32) -> bool` that is true
  when `mask` has exactly `k` set bits and they are adjacent. First test:
  `is_run_of(0b0_1111_1000_0000, 5) == true`.
- **Done when:** It agrees with a naive loop for every `u16` and every `k` in
  `1..=13` (exhaustive test, 65,536 × 13 cases).
- **Exercism:**
  [Eliud's Eggs](https://exercism.org/tracks/rust/exercises/eliuds-eggs)
  (difficulty 1) — you write popcount yourself, the first half of this
  straight test.
  `exercism download --track=rust --exercise=eliuds-eggs`
- <details><summary>Hint</summary>`let low = mask & mask.wrapping_neg();` is
  the lowest set bit. Then `mask / low` shifts the run down to bit 0, and
  you compare with `(1 << k) - 1`. Target: O(1).</details>

## 4. Binomial coefficient, multiplicative formula — `EquityEngine::n_choose_k`

- **Where:** `src/analysis/equity/engine.rs:384-397`
- **Level:** Warm-up
- **Pattern:** binomial coefficient C(n, k) by the multiplicative formula,
  with symmetry and saturation
- **Code now:**
  ```rust
  fn n_choose_k(n: u64, k: u64) -> u64 {
      if k > n {
          return 0;
      }
      let k = k.min(n - k);
      let mut result: u128 = 1;
      for i in 0..k {
          result = result * u128::from(n - i) / u128::from(i + 1);
          if result > u128::from(u64::MAX) {
              return u64::MAX;
          }
      }
      result as u64
  }
  ```
- **What it does now:** It sizes the runout space, for example C(48, 5) for
  a preflop heads-up. It uses C(n, k) = C(n, n−k) to keep the loop short.
  Cost of the excerpted site: O(min(k, n−k)) multiplies (read).
- **Learn:** After step i, `result` is C(n, i+1), which is always an
  integer. That is why the division is exact when you multiply first and
  divide second. Why is it safe to stop early at `u64::MAX`? Hint: is
  C(n, i) increasing in i while i ≤ n/2? Look up "Pascal's rule" and
  "multiplicative formula for binomial coefficients".
- **Exercise:** Write `fn choose(n: u64, k: u64) -> Option<u64>` that
  returns `None` on overflow instead of saturating, using only `u64`
  arithmetic (no `u128`). First test: `choose(52, 5) == Some(2_598_960)`.
- **Done when:** It matches a Pascal's-triangle table for all n ≤ 60, and
  `choose(67, 33)` returns `Some` while `choose(68, 34)` returns `None`.
- **Exercism:**
  [Pascal's Triangle](https://exercism.org/tracks/rust/exercises/pascals-triangle)
  (difficulty 4) — each row is C(n, 0..=n); you can build a row from the
  same multiplicative step `c * (n - i) / (i + 1)`.
  `exercism download --track=rust --exercise=pascals-triangle`
- <details><summary>Hint</summary>Divide out the gcd before you multiply:
  `g = gcd(result, i + 1)`, then `(result / g) * ((n - i) / ((i + 1) / g))`
  with `checked_mul`. Target: O(k log n).</details>

## 5. Hand-written scanner (tokenizer) — `Pluribus::parse_round`

- **Where:** `src/analysis/nubibus.rs:854-885`
- **Level:** Warm-up
- **Pattern:** single-pass lexer with one character of lookahead
- **Code now:**
  ```rust
  while i < chars.len() {
      match chars[i] {
          'f' => { events.push(PluribusEvent::Fold); i += 1; }
          'c' => { events.push(PluribusEvent::Call); i += 1; }
          'r' => {
              i += 1; // Skip 'r'
              let mut amount_str = String::new();
              while i < chars.len() && chars[i].is_ascii_digit() {
                  amount_str.push(chars[i]);
                  i += 1;
              }
              if let Ok(amount) = amount_str.parse::<usize>() {
                  events.push(PluribusEvent::Raise(amount));
              }
          }
          _ => i += 1,
      }
  }
  ```
- **What it does now:** It turns `r200ffc` into `Raise(200), Fold, Fold,
  Call` (ran). Unknown characters are skipped. A bare `r` with no digits is
  dropped: `"r"` gives `[]` and `"rXc"` gives `[Call]` (ran). Cost of the
  excerpted site: O(len) time, plus one `Vec<char>` copy and one `String`
  per raise (read).
- **Learn:** A lexer reads characters and emits tokens. The "maximal munch"
  rule takes the longest digit run after `r`. A good lexer also decides
  what to do with bad input: skip it or report it with its position. Look
  up "lexical analysis" and "maximal munch" (Crafting Interpreters, ch. 4).
- **Exercise:** Write
  `fn lex_actions(s: &str) -> Result<Vec<Action>, LexError>` where
  `LexError` holds the byte offset of the first bad character. Work on
  `s.as_bytes()` with no extra allocation. First test:
  `lex_actions("r200ffc") == Ok(vec![Raise(200), Fold, Fold, Call])`.
- **Done when:** `lex_actions("rXc")` returns `Err` at offset 1,
  `lex_actions("r")` returns `Err` at offset 1, and a raise amount larger
  than `usize::MAX` returns `Err` and does not panic.
- **Exercism:**
  [Run-Length Encoding](https://exercism.org/tracks/rust/exercises/run-length-encoding)
  (difficulty 4) — decoding scans a digit run, then the character it
  applies to: the same "read a number, then a token" loop.
  `exercism download --track=rust --exercise=run-length-encoding`
- <details><summary>Hint</summary>Keep `pos` into the byte slice. For `r`,
  accumulate `amount = amount.checked_mul(10)?.checked_add(digit)?` while
  the next byte is a digit; zero digits is an error. Target: O(len) time,
  O(1) extra space besides the output.</details>

## 6. Binary search over a sorted table — `Five::find_in_products`

- **Where:** `src/arrays/five.rs:137-162`
- **Level:** Core
- **Pattern:** binary search (Cactus Kev evaluator, paired-hand lookup)
- **Code now:**
  ```rust
  let key = self.multiply_primes();
  let mut low = 0;
  let mut high = 4887;
  let mut mid;
  while low <= high {
      mid = usize::midpoint(high, low); // divide by two
      let product = crate::lookups::products::PRODUCTS[mid] as usize;
      if key < product {
          high = mid - 1;
      } else if key > product {
          low = mid + 1;
      } else {
          return mid;
      }
  }
  0
  ```
- **What it does now:** It finds the index of a hand's prime product in the
  sorted 4,888-entry `PRODUCTS` table. Cost of the excerpted site:
  O(log 4888), at most 13 probes (read). A miss returns `0`, which is also
  the index of a real entry (`PRODUCTS[0] == 48`, four deuces and a trey):
  the straight `A K Q J T` (product 31,367,009, not in the table) returns
  index `0` (ran). `hand_rank_value` only calls it for paired hands, so the
  miss does not happen there today.
- **Learn:** Binary search keeps an invariant: "if the key is present, it
  is in `[low, high]`". The inclusive `high` form needs `mid - 1`, which
  underflows a `usize` when `mid == 0`. Can `key < 48` ever reach line 154?
  The half-open form `[low, high)` avoids that question. Look up "binary
  search invariant" and "lower_bound" (Knuth, TAOCP vol. 3, §6.2.1).
- **Exercise:** Write `fn find(table: &[u32], key: u32) -> Option<usize>`
  with a half-open `[low, high)` loop, no subtraction from `mid`. First
  test: `find(&[48, 72, 80], 72) == Some(1)`.
- **Done when:** It agrees with `table.binary_search(&key).ok()` for every
  key in `0..=table.last()+1` on the real `PRODUCTS` table, and keys below
  48 return `None` without panic.
- **Exercism:**
  [Binary Search](https://exercism.org/tracks/rust/exercises/binary-search)
  (difficulty 4) — the same halving search over a sorted slice, returning
  `Option<usize>` for a miss.
  `exercism download --track=rust --exercise=binary-search`
- <details><summary>Hint</summary>Loop while `low < high`; if
  `table[mid] < key` set `low = mid + 1`, else set `high = mid`. After the
  loop, check `table.get(low) == Some(&key)`. Target: O(log n), no
  sentinel.</details>

## 7. Prime product as a multiset key — `Five::multiply_primes`

- **Where:** `src/arrays/five.rs:165-171`; used as a lookup key in
  `src/arrays/five.rs:137-162` and in the razz ranker
  `src/games/razz/california.rs:7623-12521`
- **Level:** Core
- **Pattern:** order-independent multiset hashing by unique prime
  factorization
- **Code now:**
  ```rust
  pub fn multiply_primes(&self) -> usize {
      (self.first().get_rank_prime()
          * self.second().get_rank_prime()
          * self.third().get_rank_prime()
          * self.forth().get_rank_prime()
          * self.fifth().get_rank_prime()) as usize
  }
  ```
- **What it does now:** Each rank maps to a prime (2 → 2, … A → 41). The
  product of five primes names the multiset of ranks, in any card order.
  For example `5 4 3 2 A` gives 8,610 (ran). Cost of the excerpted site:
  O(1), four multiplies (read). The razz ranker first matches the 13-bit
  rank mask, and only for paired hands falls back to a `match` on the
  product.
- **Learn:** By the fundamental theorem of arithmetic, two multisets of
  primes have the same product only if they are the same multiset. So the
  product is a perfect key that ignores order. The cost: the key grows fast
  (41⁵ ≈ 116 million), so it needs a sorted table or a hash, not a direct
  array. Compare with a sorted-letters key and a count-vector key. Look up
  "Gödel numbering" and "anagram grouping".
- **Exercise:** Write
  `fn group_anagrams(words: &[&str]) -> Vec<Vec<String>>` with a prime
  product key per word (`a` → 2, `b` → 3, … `z` → 101), using `u128` and
  `checked_mul`. First test: `["stop", "pots", "tops", "opt"]` gives two
  groups.
- **Done when:** It gives the same groups as a sorted-letters key on a word
  list, and a word whose product would overflow `u128` falls back to the
  sorted key instead of panicking.
- **Exercism:**
  [Anagram](https://exercism.org/tracks/rust/exercises/anagram)
  (difficulty 4) — "same letters, any order" is the same multiset-equality
  test the prime product answers for ranks.
  `exercism download --track=rust --exercise=anagram`
- <details><summary>Hint</summary>Two keys are equal exactly when the
  multisets are equal. A 26-entry count array is the overflow-free version
  of the same key. Target: O(total letters).</details>

## 8. Fixed k-combinations, best-of-n — `Seven::hand_rank_value_and_hand`

- **Where:** `src/arrays/seven.rs:201-216` (loop) and
  `src/arrays/seven.rs:28-50` (the 21-row table); the general form is
  `src/analysis/equity/engine.rs:225-247` (`exact_enumerate`, via
  `itertools::combinations`)
- **Level:** Core
- **Pattern:** k-combinations in lexicographic order; argmax over them
- **Code now:**
  ```rust
  fn hand_rank_value_and_hand(&self) -> (HandRankValue, Five) {
      if !self.is_dealt() {
          return (NO_HAND_RANK_VALUE, Five::default());
      }
      let mut best_hrv: HandRankValue = NO_HAND_RANK_VALUE;
      let mut best_hand = Five::default();

      for perm in Seven::FIVE_CARD_PERMUTATIONS {
          let hand = self.five_from_permutation(perm);
          let hrv = hand.hand_rank_value();
          if (best_hrv == 0) || hrv != 0 && hrv < best_hrv {
              best_hrv = hrv;
              best_hand = hand;
          }
      }
      // ...
  ```
- **What it does now:** It tries all C(7, 5) = 21 five-card hands, written
  out by hand as index rows, and keeps the best (lowest) value. Cost of the
  excerpted site: 21 evaluations per seven cards (read). The table is named
  `PERMUTATIONS`, but the rows are combinations: is `[0,1,2,3,4]` different
  from `[4,3,2,1,0]` here?
- **Learn:** k-combinations of n in lexicographic order come from one rule:
  find the rightmost index that can still grow, add one, and reset every
  index to its right. Equivalently, C(7, 5) = C(7, 2): pick the two cards
  to drop. Look up "lexicographic combination generation" (TAOCP vol. 4A,
  Algorithm L) and "Gosper's hack" for the bitmask form.
- **Exercise:** Write
  `fn combinations(n: usize, k: usize) -> Vec<Vec<usize>>` in lexicographic
  order with no recursion. First test: `combinations(7, 5)` equals
  `Seven::FIVE_CARD_PERMUTATIONS` row by row.
- **Done when:** `combinations(n, k).len() == C(n, k)` for all n ≤ 12, and
  each output is strictly increasing and in lexicographic order.
- **Exercism:** none fits.
- <details><summary>Hint</summary>Start at `[0, 1, …, k-1]`. Find the
  largest i with `c[i] < n - k + i`; if none, stop. Then `c[i] += 1` and
  `c[j] = c[j-1] + 1` for all j > i. Target: O(k) per combination.</details>

## 9. Side pots: sort + merge runs, capped layers — `TableEquity::winnings`

- **Where:** `src/casino/equity/table_equity.rs:259-285` (`winnings`) and
  `src/casino/equity/table_equity.rs:141-167` (`consolidate`)
- **Level:** Core
- **Pattern:** layered pot split (water-filling by contribution level);
  sort then merge adjacent equal keys; seat set as a bitmask
- **Code now:**
  ```rust
  let winner_chips = self
      .0
      .iter()
      .find(|e| e.seats != Seatbit::NONE && (e.seats & sb) != Seatbit::NONE)?
      .chips;
  // ...
  for equity in &self.0 {
      let num_seats = if equity.seats == Seatbit::NONE { 1 } else { equity.seats.count_ones() };
      let taken_per_seat = equity.chips.min(winner_chips);
      total_winnings += taken_per_seat * num_seats;
      let leftover = equity.chips.saturating_sub(winner_chips);
      if leftover > 0 {
          remaining.push(SeatEquity::new(leftover, equity.seats));
      }
  }
  ```
- **What it does now:** The winner takes `min(chips, winner_chips)` from
  every contributor. Everyone's leftover forms the next pot. Checked with
  stacks 500 / 300 / 100 all in plus 50 from a folded seat: seat 0 wins
  350, then seat 1 wins 400 from the rest, and 200 goes back to seat 2
  (ran). Cost of the excerpted site: O(entries) per pot; `consolidate` is
  O(m log m) for its sort (read).
- **Learn:** Side pots are layers. Sort the distinct contribution levels
  `l1 < l2 < …`; layer i holds `(li − li−1) × (players who put in ≥ li)`
  and only those players can win it. This is the same shape as "water
  filling" and as computing a histogram's area by levels. Look up "side
  pot calculation" and "run-length grouping after sort".
- **Exercise:** Write
  `fn side_pots(contrib: &[(u64, bool)]) -> Vec<(u64, Vec<usize>)>` where
  each entry is (chips put in, still in hand). Return each pot's size and
  the indexes eligible to win it. First test:
  `side_pots(&[(100, true), (300, true), (500, true), (50, false)])` gives
  `[(350, [0,1,2]), (400, [1,2]), (200, [2])]`.
- **Done when:** The pot sizes always sum to the total chips put in, and a
  folded player's chips appear in pots but never in an eligible list.
- **Exercism:** none fits.
- <details><summary>Hint</summary>Sort the distinct levels of the players
  still in hand. Walk them once; for each level, take
  `min(contrib, level) − min(contrib, previous_level)` from every player,
  folded ones included. Target: O(p log p).</details>

## 10. Monte Carlo with rejection sampling — `EquityEngine::sample_once`

- **Where:** `src/analysis/equity/engine.rs:284-328` (`sample_once`),
  `src/analysis/equity/engine.rs:331-339` (`pick_range`),
  `src/analysis/equity/engine.rs:342-351` (`draw`)
- **Level:** Core
- **Pattern:** Monte Carlo estimation; sampling without replacement by
  rejection
- **Code now:**
  ```rust
  fn draw(remaining: &[Card], taken: &HashSet<Card>, rng: &mut SmallRng) -> Option<Card> {
      for _ in 0..256 {
          let card = remaining[rng.random_range(0..remaining.len())];
          if !taken.contains(&card) {
              return Some(card);
          }
      }
      None
  }
  ```
- **What it does now:** To deal a card that nobody holds, it picks at random
  and retries on a collision, up to 256 times. A failed sample returns
  `None` and is skipped. Cost of the excerpted site: expected
  `|remaining| / (|remaining| − |taken|)` tries per card (read).
- **Learn:** Rejection sampling is simple, but its cost grows as the free
  pool shrinks. Skipping failed samples can also bias the estimate: are
  the samples that fail in `pick_range` (64 tries) spread evenly across
  matchups, or do they fall more on crowded ranges? A partial
  Fisher–Yates shuffle draws k cards with no rejection at all. Look up
  "Fisher–Yates shuffle", "rejection sampling", and "standard error of a
  Monte Carlo estimate" (σ/√N).
- **Exercise:** Write

  has 5 distinct cards.
- **Done when:** Over 1,000,000 draws of k = 2 from 4 cards, each of the 6

  and the function never loops more than k times.
- **Exercism:** none fits.
- <details><summary>Hint</summary>For i in 0..k: pick `j` in `i..len`, swap
  `pool[i]` and `pool[j]`. Remove taken cards from the pool before you
  start. Target: O(k) per sample, zero rejections.</details>

## 11. Counterfactual regret minimization + regret matching — `KuhnCfr::cfr`

- **Where:** `src/games/kuhn.rs:976-1025` (`cfr`),
  `src/games/kuhn.rs:1029-1054` (`current_strategy`); the river solver's
  version is `src/analysis/gto/regret.rs`
- **Level:** Stretch
- **Pattern:** vanilla CFR on a game tree (recursive DFS) with regret
  matching
- **Code now:**
  ```rust
  for (i, &action) in actions.iter().enumerate() {
      let next = state.apply(action)?;
      let child_util = if player == 0 {
          self.cfr(&next, p0 * strategy[i], p1)?
      } else {
          self.cfr(&next, p0, p1 * strategy[i])?
      };
      action_utils[i] = -child_util; // flip to current player's frame
      node_util += strategy[i] * action_utils[i];
  }
  let opp_reach = if player == 0 { p1 } else { p0 };
  let my_reach = if player == 0 { p0 } else { p1 };
  let regrets = self.regret_sum.entry(info_set.clone()).or_insert_with(|| vec![0.0; n]);
  for i in 0..n {
      regrets[i] += opp_reach * (action_utils[i] - node_util);
  }
  // ... strategy_sum += my_reach * strategy
  ```
- **What it does now:** One DFS walks the whole Kuhn tree. At each decision
  it plays the current mixed strategy, measures how much better each pure
  action would have been, and adds that regret, weighted by the opponent's
  reach. `current_strategy` turns positive regrets into probabilities.
  Cost of the excerpted site: O(tree nodes) per iteration, plus one
  `info_set.clone()` per node (read).
- **Learn:** Regret matching plays each action in proportion to its positive
  regret. In a two-player zero-sum game, the *average* strategy of CFR goes
  to a Nash equilibrium at rate O(1/√T). Why does the code store
  `strategy_sum` weighted by `my_reach`, and not the last strategy? Look
  up Neller & Lanctot, "An Introduction to Counterfactual Regret
  Minimization" (2013), section 3 (the Kuhn example).
- **Exercise:** Write `fn rps_regret_matching(iterations: u32) -> [f64; 3]`
  that trains rock-paper-scissors self-play with regret matching only (no
  tree) and returns the average strategy. First test: after 100,000
  iterations, each entry is within 0.01 of 1/3.
- **Done when:** It converges for a biased payoff (rock beats scissors for
  +2) to the analytic equilibrium, and the last-iterate strategy is shown
  to cycle while the average converges.
- **Exercism:** none fits.
- <details><summary>Hint</summary>Each iteration: strategy from positive
  regrets (uniform if none); compute the expected value of each action
  against the opponent's current mix; regret += action value − strategy
  value; strategy_sum += strategy. Target: O(actions) per
  iteration.</details>

## 12. Brute-force best response by bitmask enumeration — `KuhnStrategy::best_response_value`

- **Where:** `src/games/kuhn.rs:1073-1100`
- **Level:** Stretch
- **Pattern:** subset enumeration with a bitmask (`for bits in 0..2^k`);
  best response / exploitability
- **Code now:**
  ```rust
  fn best_response_value(&self, br_player: usize) -> f64 {
      let mut best = f64::NEG_INFINITY;
      for bits in 0u32..64 {
          let first = [bits & 1 != 0, (bits >> 1) & 1 != 0, (bits >> 2) & 1 != 0];
          let second = [(bits >> 3) & 1 != 0, (bits >> 4) & 1 != 0, (bits >> 5) & 1 != 0];
          let total: f64 = DEALS
              .iter()
              .map(|&(c0, c1)| self.eval_deal_policy(br_player, c0, c1, first, second))
              .sum();
          let avg = total / 6.0;
          if avg > best {
              best = avg;
          }
      }
      best
  }
  ```
- **What it does now:** Each of the 6 bits is one yes/no choice at one
  information set. So the 64 values of `bits` are all 64 pure policies. It
  scores each one over the 6 deals and keeps the best. Cost of the
  excerpted site: 2⁶ × 6 = 384 deal evaluations (read).
- **Learn:** k independent yes/no choices are exactly the integers
  `0..2^k`; bit i is choice i. This is fine for k = 6 and hopeless for
  k = 40. A best response can instead be found by one tree walk that picks
  the max action at each information set, which is linear in the tree size.
  Why must the walk sum over the opponent's hidden card *before* it picks
  the max? Look up "best response in extensive-form games" and
  "exploitability".
- **Exercise:** Write
  `fn best_subset(values: &[i32], max_size: u32) -> (u32, i32)` that
  enumerates all masks `0..1 << values.len()`, skips masks with more than
  `max_size` set bits, and returns the mask with the highest sum. First
  test: `best_subset(&[3, -1, 4], 2) == (0b101, 7)`.
- **Done when:** It matches a recursive include/exclude search for every
  slice of length ≤ 16, and a second version iterates only masks with at
  most `max_size` bits (Gosper's hack).
- **Exercism:**
  [Secret Handshake](https://exercism.org/tracks/rust/exercises/secret-handshake)
  (difficulty 4) — you decode an integer's bits into a list of choices,
  which is what `first` and `second` do with `bits`.
  `exercism download --track=rust --exercise=secret-handshake`
- <details><summary>Hint</summary>`for mask in 0u32..(1 << n)`; bit i on
  means "take item i"; `mask.count_ones()` checks the size. For the tree
  version: at the best responder's nodes, sum child values across the
  opponent's possible cards weighted by their reach, then take the
  max. Target: O(2^k · cost) brute force, O(tree) by tree walk.</details>
